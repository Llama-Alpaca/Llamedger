# Llamedger（羊驼记账）

一个 Android 自动记账 App。核心理念：**你不用手动记账，付款后它自己记**；**商家退款时，它把对应的那笔支出直接抹掉**。

---

## 关于这个项目

**Llamedger = Llama（羊驼）+ Ledger（账本）**。

一个**没有用 IDE、没有用 Android Studio、没有用 Gradle** 的 Android 项目。

- 构建：`build.py` 直接调用 SDK 原生工具链（aapt2 → javac → d8 → zipalign → apksigner），
  跳过 Gradle。清理后完整构建约 **6.5 秒**
- 语言：Java + Android 平台原生 API，**零第三方依赖**，APK 约 86 KB
- 测试：业务逻辑刻意与 Android 解耦，可在电脑上用 `javac` + `java` 直接跑
- 详见 [第五节 构建与测试](#五构建与测试)

> **免责声明**
> 本项目为个人自用工具，需要「通知使用权」来读取支付通知，请自行评估隐私风险。
> 所有数据仅存于本机 SQLite，不联网、不上传。代码按 MIT 协议开源，使用后果自负。

## 一、它做什么

| 能力 | 说明 |
|---|---|
| 自动识别消费 | 监听**招商银行 App 推送通知**（主力），自动解析金额、商户、卡号、时间并入账 |
| 多通道兜底 | 微信支付通知、支付宝通知、云闪付；银行短信（可选开启） |
| **退款自动冲销** ★ | 识别到退款/退回（含微信转账 24 小时过期退回）时，自动找到对应的原支出并**整条移除**；部分退款则冲减原金额 |
| **内部转账识别** | 微信/支付宝提现到银行卡、充值、信用卡还款这类「钱在自己账户间搬家」的操作，会自动配对成一条转账，**不计入收支** |
| 自动去重 | 同一笔消费被招行和微信各报一次时，只记一条，并回填更完整的商户信息 |
| 自动分类 | 按商户关键词归类到餐饮/交通/购物/居住/通讯/娱乐/医疗/教育/人情/旅行/金融等 |
| 基础记账功能 | 手动记账、流水列表、搜索筛选、编辑删除、分类统计、月度趋势、CSV 导出 |
| 顺手删除 | 长按流水条目弹出操作菜单即可删除；点进编辑页底部也有删除按钮 |
| **识别诊断** | 设置 → 识别诊断：看通知有没有到达、来自哪个包名、有没有被识别 |
| 后台常驻 | 前台服务保活 + 开机自启 + 电池优化白名单引导 |

**隐私**：所有数据只存在手机本机 SQLite，App 不联网、不上传、无网络权限。

## 二、退款自动冲销是怎么工作的 ★

这是本项目的核心特色，实现位于 `core/engine/RefundEngine.java`。

### 1. 先判断「这是不是一笔退款」

命中关键词即判定为退款事件（`core/parse/Lexicon.java` → `REFUND_WORDS`）：

```
退款 退回 退还 退货 返还 冲正 逆冲 原路退回 资金退回 交易撤销
超时退回 自动退回 转账退回 退款到账 已退款 refund reversal …
```

### 2. 再往回找「它退的是哪一笔」

在回溯窗口内（默认 90 天）取出所有有效支出，逐条**打分**：

| 维度 | 加分 |
|---|---|
| 金额与剩余金额完全一致 | +60 |
| 部分退款（退款额 < 原支出） | +40 |
| 商户名完全相同 | +25 |
| 商户名互相包含 | +15 |
| 商户名明显不同 | **−35** |
| 退款发生在 1 小时内 | +20 |
| 24 小时内 / 7 天内 / 30 天内 / 90 天内 | +18 / +14 / +8 / +3 |
| 账户或渠道一致 | +10 |
| 来源通道一致 | +5 |
| 转账退回且原分类是「转账」 | +10 |
| 金额悬殊且商户信息缺失 | −10 |

### 3. 双保险，防误删

只靠分数还不够 —— **必须有至少一项「佐证」**才会真的动账：

1. 商户名能对上（相同或互相包含），或
2. 发生在 24 小时内，或
3. 是转账退回且原支出分类为转账/人情，或
4. 同一渠道且 7 天内

> 这一条防的是「两个月前刚好也有一笔 100 元支出」这种纯金额巧合被误删。
> 对应测试用例：`防误删-纯金额巧合不冲销`。

### 4. 执行动作

- **全额退款** → 原支出 `status = 已撤销`（软删除，列表里显示删除线 + 「已撤销」角标）
- **部分退款** → 原支出 `refunded_cents += 退款额`，金额自动变成剩余值
- 退款本身**不计入收入**（`original_txn_id != 0` 的记录会被统计忽略），避免和「原支出已移除」重复计算
- 写入 `refund_link` 审计记录，**任何一笔都能一键恢复**
- 默认策略：**自动移除**；可在设置里改为「标记待确认」，由你手动点头

### 5. 匹配不到原支出怎么办

记为一笔普通收入（分类「退款」），备注里写明「未匹配到原支出」以及最高分候选的说明，方便你人工核对。

## 三、安装

```powershell
# 已构建好的安装包
dist\jizhang-assistant.apk
```

传到手机安装（需允许「安装未知来源应用」）。首次打开会引导你开启权限：

1. **通知使用权（必开）** — 设置 → 通知和状态栏 → 通知使用权 → 记账助手 → 打开
   这是自动记账能工作的前提，招行/微信/支付宝的付款推送都靠它。
2. **自启动 + 电池白名单（强烈建议）** — 国产 ROM 默认清理后台，不加白名单可能收不到通知。
3. **银行短信（可选）** — 你的招行走 App 通知，这项不开不影响主要功能。

```
├── tools/icon_preview.py             把图标转成字符画，便于无图形环境时自检构图
├── tools/make_icons.py               羊驼图标方案绘制
├── tools/gen_icon_assets.py          生成各密度图标（传统 + 自适应 + 状态栏）
├── tools/check_resources.py          静态检查：控件 id、布局、自定义 View 是否匹配
├── tools/check_migration.py          静态检查：数据库升级不丢数据
├── build.py                          构建 APK（不依赖 Gradle）
└── run_tests.py                      跑核心逻辑测试
```

### 分层原则

`core/` 里**不出现任何 `import android.*`**，所以整套业务逻辑能在电脑上用普通 `javac` 编译运行，
不必装模拟器就能验证解析与退款匹配是否正确。数据访问通过 `TxnStore` 接口抽象，
Android 端用 SQLite 实现（`db/SqliteStore.java`），电脑端用内存实现（`tests/MemoryStore.java`）。

### 数据流

```
招行 App 推送 / 微信通知 / 银行短信
      ↓
NotifyListenerService / SmsReceiver        (capture)
      ↓
Monitor.handle                             (capture)  落原文 → 解析 → 去重 → 入账
      ↓
EventParser → BankParser / NotificationParser   (core.parse)
      ↓
IngestEngine                               (core.engine)  编排 + 去重
      ↓
RefundEngine                               (core.engine)  ★ 退款冲销
      ↓
SqliteStore                                (db)
      ↓
MainActivity / TxnListActivity / StatsActivity / SettingsActivity   (ui)
```

## 七、内部转账为什么必须单独处理

「从微信零钱提现 3000 元到招行卡」会产生两条通知：

```
微信：零钱提现成功，预计2小时内到账，金额3000.00元
招行：您尾号1234的账户于08月29日14:30收款人民币3000.00元
```

钱只是从你自己的一个口袋换到另一个口袋，**既不是支出也不是收入**。
如果按普通流水记账，会同时虚增 3000 元支出和 3000 元收入，账面全错。

但现实里常常只有一条有金额。微信的提现通知长这样：

```
微信支付 | [2条]微信支付: 零钱提现已到账     ← 完全没有金额
```

处理方式分两条路径（`core/engine/TransferEngine.java`）：

**路径 A：两侧都有金额 → 直接配对**

1. 命中「提现 / 充值 / 零钱通 / 信用卡还款」等关键词的流水，标记 `is_transfer = 1`
2. 配对引擎在 **±3 天、金额一分不差** 的范围内，为它找到方向相反的另一半
   （约束：至少一方已明确是内部转账，避免「金额相同的一进一出」被误配）
3. 配对成功后双方互相关联，**双双从收支统计中排除**，流水列表显示为「转账·已配对」

**路径 B：提现通知没有金额 → 走「转账线索」**

1. 解析失败但文案含「提现/充值」关键词 → 记下一条线索（含时间戳），不产生假流水
2. 银行那侧「收款 xxx 元」到达时，若 **±2 小时** 内存在未消费的线索 → 判定为转账而非收入
3. 线索用掉即标记为已消费，避免被套用到下一笔流水上

这样能保证：真·提现入账不会虚增收入，而朋友转给你的钱仍然正常算收入。

退款引擎也会跳过转账流水 —— 转账不是消费，不该被退款冲销。
长按任意一条流水还可以手动「标记为转账」或「取消转账配对」。

## 八、金额解析为什么要「候选打分」

早期版本采用「正则第一个匹配就返回」，踩了一个严重的坑：

```
微信支付 | 零钱提现成功，预计2小时内到账，金额3000.00元
```

方向词「支付」后面允许跨 8 个任意字符，于是够到了后面无关的数字。
实际踩到的两次：

| 通知原文 | 被误抓的数 | 来源 |
|---|---|---|
| `微信支付 \| 零钱提现成功，预计2小时内到账，金额3000.00元` | `2` | 「2**小时**内到账」 |
| `微信支付 \| [2条]微信支付: 零钱提现已到账` | `2` | 「[2**条**]」通知分组计数 |

两次都被记成了一笔 **2 元支出**。

现在 `AmountParser` 的做法是：

1. **收窄方向词锚定** —— 金额必须紧跟方向词，只允许「金额/为/是」这类少量连接词
2. **收集所有候选**，不再命中即返回
3. **剔除假金额** —— 余额/额度后面的数字、后面紧跟数量单位的数字（小时/分钟/天/条/位/张…）、
   被括号整个包住的数字（`[2条]`、`[3]`、`【2】`）
4. **按上下文打分** —— 带货币符号 > 后跟「元」> 带小数 > 带千分位，取得分最高者

## 九、应用图标是怎么做出来的

图标是一只小羊驼侧脸（`D_profile` 方案）。这台开发机上**没有任何图像库**（PIL / cairosvg / numpy 都没装），
AI 生图工具也不可用，所以图标是用一套自写的纯 Python 光栅化器画出来的：

1. `tools/icon_renderer.py`
   - 用几何方程（椭圆、圆角矩形、多边形）逐像素填充，支持旋转椭圆
   - 在 3 倍尺寸上绘制，再按面积平均降采样 → 得到平滑的抗锯齿边缘
   - 自己实现 PNG 编码（zlib 压缩 + CRC 校验），不依赖 Pillow
2. `tools/icon_preview.py`
   - 把渲染结果转成**字符画**，这样在看不到图片的环境里也能检查构图
     （哪块是背景、耳朵在哪、眼睛有没有和口鼻挤在一起）
   - 开发中靠它发现并修正了两轮问题：五官间距过近、浅色羊驼与浅色背景对比度不足
3. `tools/gen_icon_assets.py`
   - 传统图标：`mipmap-{m,h,xh,xxh,xxxh}dpi/ic_launcher.png`（48 → 192px）
   - 自适应图标：`mipmap-anydpi-v26/ic_launcher.xml` + 透明底前景 PNG（108 → 432px）
   - 状态栏通知图标：`drawable-*/ic_stat_jz.png`（24 → 96px，白色剪影）

要改图标，直接改 `tools/make_icons.py` 里的绘制函数，然后跑：

```powershell
python tools\make_icons.py          # 生成预览（输出到 preview/icons/）
python tools\gen_icon_assets.py     # 生成 App 内全套图标资源
```

## 十一、收不到账时怎么自查

App 里内置了「**设置 → 识别诊断**」，用来回答三个问题：

| 现象 | 说明 |
|---|---|
| 「最近收到的通知」一直是空的 | 通知**根本没到达**本应用。检查「通知使用权」是否被系统关闭（ROM 升级、应用重装后常发生），以及银行 App 自身的「动账通知」开关是否打开 |
| 有记录但标记为「未识别」 | 通知到了，但来源包名不在白名单且内容判断也不像银行交易。把包名和标题发来即可补规则 |
| 有记录、标记「已识别」，但没有流水 | 解析或去重环节有问题。请把通知原文发来，据此加回归测试 |

顶部「权限与开关」会逐项检查：通知使用权、监听服务连接、自动记账总开关、后台常驻服务。
本页**只记录通知的来源应用与标题，不保存通知正文**。

### 关于包名匹配

早期版本用一份**硬编码的精确包名名单**来筛选通知，这是「消费完全没有记录」的元凶：
银行 App 的包名常随版本变化（招商银行就有 `cmb.pb`、`com.cmbchina.*` 等多种写法），
只要对不上，通知就被**静默丢弃且不留任何痕迹**。

现在改成三级判断：

1. 精确名单命中
2. **模糊特征**：包名里含 `cmb` / `bank` / `icbc` / `unionpay` 等片段即认
3. **文本兜底**：包名完全不认识时，若文本同时含「银行特征词 + 交易行为词 + 金额」，也认

这样即使银行换了包名，消费也不会再漏记。

## 十二、已知限制

1. **依赖通知可见性** — 如果用户把招行 App 的通知权限关了，或系统把通知折叠/静默，就抓不到。所以「通知使用权 + 电池白名单」两项必须开。
2. **富文本通知** — 部分 ROM 会对通知做摘要合并，导致正文被截断。`NotifyListenerService` 已按「大文本 → 多行 → 普通文本 → 副文本」优先级取最完整的一份。
3. **商户名依赖文案** — 招行推送里带商户名时能精确匹配；不带时退款匹配会退化为「金额 + 时间」判断，此时更容易落到「未匹配」而记成收入，需要人工核对。
4. **微信转账过期退回** — 通知文案因版本而异，已内置多种关键词；遇到没覆盖的文案，往 `Lexicon.REFUND_WORDS` 补词即可。
5. **未做多账户余额联动** — 账户目前只是一个标签，不跟踪余额。
6. **转账线索窗口 2 小时** — 若银行入账推送延迟超过 2 小时，线索会失效，那笔收款会被记成收入，
   需要长按手动「标记为转账」。同一时间窗内若有多笔入账，线索只会作用于最先到达的那一笔。
7. **targetSdk 33** — 未上架应用商店，仅供个人侧载使用。
